One authorization server serves all six Google packs: [`gmail`](/packs/gmail),
`gcalendar`, `gsheets`, `gdocs`, `gdrive` and `gforms`. One client registration, one consent
screen, one refresh token, one [`OAuth2Client`](/reference/oauth#oauth2client) handed to all six.

## The server

```python google_server.py
from charter.auth import OAuth2Server, Revocation

GOOGLE = OAuth2Server(
    issuer="https://accounts.google.com",
    authorization_endpoint="https://accounts.google.com/o/oauth2/v2/auth",
    token_endpoint="https://oauth2.googleapis.com/token",
    token_endpoint_auth_method="client_secret_post",
    authorization_params={"access_type": "offline", "prompt": "consent"},
    revocation=Revocation("https://oauth2.googleapis.com/revoke", auth_method="none"),
)
```

This is the canonical copy. `scripts/live_google_check.py` holds the same
constant in Python and fails if Google's own discovery document stops agreeing
with it.

[`revocation`](/reference/oauth#revocation) is how a user is disconnected: [Disconnecting](#disconnecting).
Google documents its revocation endpoint with the token alone, so
`auth_method="none"` keeps the client secret out of that request.

Google does publish metadata, so
`await OAuth2Server.discover("https://accounts.google.com")` builds the same
three endpoint fields at the cost of a network round trip at import time. What
it can never fill in is `authorization_params` — see below, because that is the
field the whole integration turns on.

## Scopes

Each tool lists the scopes Google's reference accepts for its method, narrowest
first, leaving out any that reach only part of what the tool can do.
[`scopes_for`](/reference/oauth#scopes_for) then picks the narrowest set that
covers the tools you hand out. Every scope is under
`https://www.googleapis.com/auth/` except the full-mailbox one:

The category is what launching costs: any restricted scope means a security
assessment before other people can connect, repeated every year, and a sensitive
one means Google's verification without it. Hand out tools, not packs, and the
consent screen follows:

```python gmail_narrow_scopes.py
from charter.auth import scopes_for
from charter.packs import gdocs, gmail

scopes_for([gmail.messages_send])                        # ['…/gmail.send']: no assessment
scopes_for([gdocs.documents_create])                     # ['…/drive.file']: no review at all
scopes_for([gmail.threads_list, gmail.threads_modify])   # ['…/gmail.modify']
scopes_for(gmail.TOOLS)                                  # ['https://mail.google.com/']
```

The third asks for `gmail.modify` alone: it covers reading as well, and a grant
of both would be no wider. Only `threads_delete` needs the full mailbox, and it
covers every other Gmail tool, so the whole pack asks for that one scope.

`drive.file` reaches only files your app created or the user opened with it,
which is why only `files_create`, `about_get` and the three create tools in Docs,
Sheets and Forms offer it. `files_create` under it can create at the root or in a
folder your app made; a `parents` folder the user made needs `drive`.

```python google_scopes.py
from charter.auth import scopes_for
from charter.packs import gcalendar, gdocs, gdrive, gforms, gmail, gsheets

CONNECT_SCOPES = scopes_for([*gmail.TOOLS, *gcalendar.TOOLS, *gsheets.TOOLS, *gdocs.TOOLS, *gdrive.TOOLS, *gforms.TOOLS])
```

Ask for these in one authorization request and one refresh token covers all
six packs. Adding a pack later means sending the user back through consent: a
grant covers the scopes it was issued for and nothing else, and the failure when
it does not is a `403` from the API, not from the token endpoint.

Each pack also reads the environment, so a script or the
[MCP server](/using/mcp) needs no wiring at all. All six renew a grant from
`$GOOGLE_TOKEN_FILE` (an authorized-user JSON file) or from
`$GOOGLE_REFRESH_TOKEN` with `$GOOGLE_CLIENT_ID` and `$GOOGLE_CLIENT_SECRET`,
through one shared client built on the server above. Failing those they read
`$GOOGLE_ACCESS_TOKEN`, the static-token path, which never refreshes. The order
is on [environment fallbacks](/reference/configuration#environment-fallbacks).

A call the grant does not cover answers 403 with the standard
`WWW-Authenticate: Bearer error="insufficient_scope", scope="…"` challenge, which
lists every scope Google would accept, legacy aliases included. Charter reads it on
any response and raises [`InsufficientScope`](/reference/errors#insufficientscope)
with the narrowest of them the tool lists.

## Wiring the packs

```python google_client.py
from charter.auth import OAuth2Client
from charter.packs import gcalendar, gdocs, gdrive, gforms, gmail, gsheets

google = OAuth2Client(
    GOOGLE,
    client_id=os.environ["GOOGLE_CLIENT_ID"],
    client_secret=os.environ["GOOGLE_CLIENT_SECRET"],
    refresh_token=stored_refresh_token,
    on_refresh=save_to_db,
)

for pack in (gmail, gcalendar, gsheets, gdocs, gdrive, gforms):
    pack.configure(credential_provider=google)
```

One client across six packs on purpose: the access token is fetched once and
cached once, so a run that sends a mail, files a calendar event and appends a
row spends one refresh rather than six. Serving many end users instead of one
account is [`SubjectProvider`](/auth/authorization-servers#serving-many-users),
which keeps one of these per subject.

## Getting the first grant

The snippets here are a web app's: a route, a session, a row per user. For one
account of your own, [Set up Google](/auth/setup/google) does the same
two protocol steps from a terminal, with no route and no database.

Charter refreshes a grant you already hold and never obtains one — the consent
redirect, `state`, PKCE and the callback route are [your framework's](/auth/oauth-flow).
Two steps of it are protocol, and they are the ones below:

```python google_connect.py
from charter.auth import OAuth2Flow

flow = OAuth2Flow(
    GOOGLE,
    client_id=os.environ["GOOGLE_CLIENT_ID"],
    client_secret=os.environ["GOOGLE_CLIENT_SECRET"],
    redirect_uri="https://app.example.com/oauth/google/callback",
)

request = flow.authorize(scopes=CONNECT_SCOPES, login_hint=user.email)
```

At the callback, check what Google actually granted before you store it:

```python google_callback.py
async def callback():
    grant = await flow.exchange(code, code_verifier=verifier)

    missing = missing_scopes(gmail.TOOLS, grant.scopes)
    if missing:
        abort(400)  # the user unticked a permission on the consent screen

    await db.grants.put(user.id, "google", grant.refresh_token)
```

Google's consent screen lets a user approve some scopes and refuse others, and
the exchange still succeeds. `grant.scopes` is what was really issued; comparing
it with [`missing_scopes`](/reference/oauth#missing_scopes) is the only place that gap is visible before a tool call
returns `403`.

[`OAuth2Client.from_grant(GOOGLE, grant, client_id=..., client_secret=...)`](/reference/oauth#oauth2client-from_grant) turns
that grant into the provider above without spending a refresh.

## Refresh behaviour

**Google does not rotate refresh tokens.** A refresh response carries an
`access_token`, an `expires_in` of about an hour, and no `refresh_token` — so
[`on_refresh`](/reference/oauth#onrefresh) hands you back the same string you passed in. The row worth writing
is the one [`exchange()`](/reference/oauth#oauth2flow-exchange) returned; `on_refresh` still earns its place as the hook
that tells your store the grant is alive.

**Concurrent refreshes are harmless here**, because nothing is invalidated by a
second one. [`OAuth2Client`](/reference/oauth#oauth2client) serialises them anyway — twelve parallel tool calls
wait on one refresh — which is what makes the same code safe against the
rotating servers on the other two provider pages.

**A revoked grant answers `invalid_grant`.** Revocation happens at
`myaccount.google.com/permissions`, or when a Workspace admin removes the app.
Charter raises [`CredentialError`](/reference/errors#credentialerror) and then
stops asking for 60 seconds, because the token endpoint rate-limits per client
and one dead user must not degrade the rest. Call [`reset()`](/reference/oauth#attributes-and-methods) after re-authorizing.

## What fails silently

**`access_type=offline` and `prompt=consent`.** Without the first, Google returns
no refresh token at all. Without the second, a returning user who already
approved your app gets a token response with no refresh token in it — Google
only re-issues one on a *consenting* authorization. Nothing errors either way:
the access token works, and the integration dies within the hour. That is why
the lore lives on the [`OAuth2Server`](/reference/oauth#oauth2server) declaration, and why [`exchange()`](/reference/oauth#oauth2flow-exchange) defaults
to `expect_refresh_token=True` and names both parameters when none comes back.

**A hundred refresh tokens per account, per client.** Google caps them and
silently invalidates the oldest when you cross the line. An app that runs the
consent flow on every login instead of reusing the stored grant will work for
its first hundred users and then start logging out the earliest ones.

**Refresh tokens expire in seven days while the app is in testing.** A Cloud
Console project whose publishing status is *Testing* issues refresh tokens that
die after a week. The symptom — works all week, `invalid_grant` on Monday — is
worth recognising before you go looking for a bug in your storage.

**`login_hint` is a hint.** It pre-fills the account chooser; the user can pick a
different account. If your product ties the grant to an email address, read the
address back from the API rather than trusting the one you asked for.

## Disconnecting

A "Disconnect Google" button has to revoke the grant, not only delete your
row. Without the revocation the refresh token keeps working, your app stays
under the user's [third-party connections](https://myaccount.google.com/connections)
with every scope it was given, and Google's refresh tokens do not expire on
their own.

```python google_disconnect.py {11}
from charter.auth import OAuth2Client

async def disconnect():
    row = await db.grants.get(user.id, "google")
    client = OAuth2Client(
        GOOGLE,
        client_id=os.environ["GOOGLE_CLIENT_ID"],
        client_secret=os.environ["GOOGLE_CLIENT_SECRET"],
        refresh_token=row.refresh_token,
    )
    await client.revoke()
    await db.grants.delete(user.id, "google")
```

[`revoke()`](/reference/oauth#attributes-and-methods) posts the refresh token
to `https://oauth2.googleapis.com/revoke`. Measured against Google, it answers
`200 {}`, every access token issued from the grant is refused in the same
second, and the refresh token comes back `invalid_grant`.

**It ends every grant your app holds for that account, not only this one.**
Revoking one Calendar grant also ended a second refresh token issued to the
same client for the same account, and a third issued for Docs. Google keeps
one authorization per account per client, and revoking removes all of it. If
you store a row per pack or per scope, disconnecting one disconnects them all,
so delete them all.

A grant already gone answers `400 invalid_token` ("Token is not revocable."),
and `revoke()` returns `False` rather than raising, since the outcome is the
one asked for. Google gives that same answer to an access token that has
lapsed while the grant behind it is still live, so revoke with the refresh
token. Handed only an access token,
[`revoke_token`](/reference/oauth#revoke_token) raises rather than return
`False` when Google calls it dead. A live access token ends the whole grant.

Serving many users through [`SubjectProvider`](/reference/credentials#subjectprovider), `await provider.revoke(user.id)`
does the lookup and the revocation, then forgets the user's client:
[Disconnecting a user](/auth/authorization-servers#disconnecting-a-user).
