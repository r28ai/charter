Fifty-six tools over one Outlook mailbox, one per Microsoft Graph v1.0 operation
and named after it: `messages_update` is `PATCH /me/messages/{id}`, which is how
Graph marks a message read, flags it, categorises it and edits a draft. Where an
operation is served at more than one path, or takes its body in more than one
format, it is still one tool — the difference is an optional argument, and the
model never chooses a URL.

## Authenticating

{/* generated:auth start — do not edit by hand; run scripts/generate_pack_docs.py */}
**Before the first call, Outlook needs a token from an app registered with Microsoft Entra.** Microsoft issues no API key for mail. [Register an app](/auth/apps/microsoft), grant it the delegated Graph permissions these tools ask for — `Mail.ReadWrite`, `Mail.Send` and `MailboxSettings.ReadWrite` cover every write — and sign in through it. To try a tool on your own mailbox first, [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer) shows the signed-in account's token on its **Access token** tab; `export MICROSOFT_ACCESS_TOKEN=…`.

This pack takes an OAuth bearer token, and [`configure()`](/reference/configuration#configure) is optional when `$MICROSOFT_ACCESS_TOKEN` is set. Which credential provider you hand it depends on whose account the calls run as.

### A token you hold

For a script, or a notebook. [`EnvTokenProvider`](/reference/credentials#envtokenprovider) re-reads the variable on every call, so a token rotated beside the process is picked up without a restart; [`StaticTokenProvider`](/reference/credentials#statictokenprovider) takes one you already hold as a string. Neither renews anything, so the calls stop when the token expires.

```python outlook_script.py {4}
from charter.auth import EnvTokenProvider
from charter.packs import outlook

credentials = EnvTokenProvider("MICROSOFT_ACCESS_TOKEN")
outlook.configure(credentials)
```

### One account, refreshed

For an agent or a server acting as you. [`OAuth2Client`](/reference/oauth#oauth2client) turns a client registration and a stored refresh token into an access token, and [renews it](/auth/authorization-servers#what-the-cache-does-precisely) before it lapses.

```python outlook_agent.py {8}
from charter.auth import OAuth2Client
from charter.packs import outlook

credentials = OAuth2Client(
    MICROSOFT,
    client_id=os.environ["MICROSOFT_CLIENT_ID"],
    client_secret=os.environ["MICROSOFT_CLIENT_SECRET"],
    refresh_token=os.environ["MICROSOFT_REFRESH_TOKEN"],
)
outlook.configure(credentials)
```

<Note>
No refresh token yet? [Getting the grant](/auth/oauth-flow) is the one-time consent flow that hands you one.
</Note>

### Many end users

For a product whose users each connect their own account. [`SubjectProvider`](/reference/credentials#subjectprovider) builds one credential per user through a factory you write, and [`use_subject`](/reference/credentials#use_subject) names the user a call acts for. [Your users' accounts](/auth/oauth-flow) is the consent route inside your app; [serving many users](/auth/authorization-servers#serving-many-users) is the per-subject cache and its eviction.

The client is handed a function that reads the stored grant, not a copy of the refresh token. A server runs several workers, and a copy goes stale the first time another worker refreshes: [More than one process](/auth/oauth-flow#more-than-one-process).

```python outlook_server.py {24,28}
from functools import partial

from charter.auth import OAuth2Client, SubjectProvider, TokenGrant, use_subject
from charter.packs import outlook

# Yours to write: a user id in, that user's credential out.
async def for_user(user_id: str) -> OAuth2Client:
    async def stored_grant() -> TokenGrant:  # read again whenever the token is due
        row = await db.grants.get(user_id, "microsoft")
        return TokenGrant(
            access_token=row.access_token,
            refresh_token=row.refresh_token,
            expires_at=row.expires_at,
        )

    return OAuth2Client(
        MICROSOFT,
        client_id=os.environ["MICROSOFT_CLIENT_ID"],
        client_secret=os.environ["MICROSOFT_CLIENT_SECRET"],
        refresh_token=stored_grant,
        on_refresh=partial(save_to_db, user_id),
    )

credentials = SubjectProvider(for_user)
outlook.configure(credentials)

# Per request: whose grant the tools use.
with use_subject(request.user_id):
    ...  # your agent runs here
```
{/* generated:auth end */}

The token is a delegated one: the tools act as the signed-in user, on `/me`.
Microsoft's authorization server publishes its metadata, so the `MICROSOFT`
constant the snippets above name is one call —
[`OAuth2Server.discover`](/auth/authorization-servers) against
`https://login.microsoftonline.com/{tenant}/v2.0`. Ask for `offline_access`
beside the Graph scopes, or Microsoft issues no refresh token.

## One operation, one tool

**Several paths.** Graph lists messages at `/me/messages` and at
`/me/mailFolders/{id}/messages`, and folders at the root and under a parent's
`childFolders`. Each is one tool: `messages_list(folder_id=...)`,
`mail_folders_list(parent_folder_id=...)`, `messages_create(folder_id=...)`,
`mail_folders_create(parent_folder_id=...)`. Leave the scope out for the wider
route. The routes are declared on the tool, most specific first, and the runtime
calls the first one the arguments fill — see [routes](/tools/wire-contract#routes).

**Two body formats.** `send_mail`, `messages_create` and the reply, reply-all and
forward operations take a JSON message *or* a MIME document. Fill `message` (and
`comment`, `toRecipients`) for JSON, or `mime` with an
[`EmailContent`](/reference/semantic-types#emailcontent) for MIME, which
[`Format("mime_base64")`](/reference/transforms#built-in-transforms) builds and
encodes in standard base64 — padded, with `+` and `/`, the alphabet Graph decodes.
`mime` is [`Body(media_type="text/plain")`](/tools/wire-contract#a-body-in-another-media-type):
set, it is the whole body and the JSON arguments are refused beside it.

**Narrower tools are a projection.** A deployment that wants an action-sized tool
derives one:

```python outlook_mark_read.py
mark_read = outlook.messages_update.derived(
    name="mark_read", keep={"message_id", "message.is_read"}
)
```

The model then sees `messageId` and `isRead`, and nothing else of the message.

## What crosses the boundary

### On the way out

A file attachment's `contentBytes` takes the file's text, and is base64-encoded
on the way out. Its description says "base64-encoded contents", which is Graph's
wire format; a [`Gloss`](/reference/markers#gloss) tells the model not to encode
it twice.

### On the way back

Graph wraps every object in envelope keys and every recipient twice. The
response handlers drop `@odata.context`, `@odata.etag`, `changeKey` and
`conversationIndex`, and flatten each recipient to `Name <address>`.
`messages_list` leaves each message's full `body` out — `bodyPreview` carries the
first 255 characters, and a selected `uniqueBody` stays, which is the way to read
a thread: `filter="conversationId eq '…'"`, `select="from,receivedDateTime,uniqueBody"`.

`messages_get` and `messages_list` ask Graph for bodies as plain text
(`Prefer: outlook.body-content-type="text"`). A host that wants the HTML — to
edit a draft in its own formatting — passes
`headers={"Prefer": 'outlook.body-content-type="html"'}` to `ainvoke`, which
applies last.

An attachment is decoded only when it is text, and strictly. A binary file is
reported by name, type and size, and `attachments_get_content` hands over its
bytes.

## Paging

Graph answers a long collection with `@odata.nextLink`, the whole URL of the next
page, and Microsoft is explicit that the `$skip` or `$skiptoken` inside it is not
for extracting. So the handlers return it as `next_link`, every paging tool takes
it back under that name, and the tool sends the link's own query string in place
of the parameters it would otherwise build.

The link also says which collection it is a page of — `mailFolders('drafts')` —
and that is a path parameter, not part of the query. So the tool takes the folder
from the link too: a `next_link` passed on its own stays in its folder, and one
passed beside a different `folder_id` follows the link. The link's path is matched
against the tool's own routes and one that matches none is refused, so a rewritten
link can change which page of which folder, never which endpoint.

```python outlook_paging.py
args = {"folder_id": "inbox", "top": 50}
page = await outlook.messages_list.ainvoke(args)
while (args := outlook.messages_list.pagination.next_page_args(page, args)) is not None:
    page = await outlook.messages_list.ainvoke(args)
```

`messages_delta` and `mail_folders_delta` end a round with `delta_link` instead. Keep
it, and pass it as `next_link` later: the next round returns only what was
created, updated or removed since.

`messages_delta` sizes its pages with `max_page_size`, which is Graph's
`Prefer: odata.maxpagesize` header, and does not offer `$top`. Graph lists `$top`
among the options delta supports, but on a delta round it ends the round: `$top=2`
on a folder of twelve messages returned two and a `delta_link`, the next round
returned nothing, and the other ten were never delivered.

## Gotchas

<AccordionGroup>
  <Accordion title="Delete does not go to Deleted Items">
    `messages_delete` (`DELETE /me/messages/{id}`) skips Deleted Items: the message
    lands in Recoverable Items (`recoverableitemsdeletions`), where Outlook keeps it
    for the retention period. A folder deleted with `mail_folders_delete` does not
    appear in Deleted Items either. To put either there, move it: `messages_move`
    or `mail_folders_move` to `deleteditems`. `messages_permanent_delete` calls
    Graph's `permanentDelete` action, after which Outlook clients cannot reach the
    message, and a folder deleted with `mail_folders_permanent_delete` is removed
    outright, not kept in the purges folder.
  </Accordion>

  <Accordion title="Some query options are accepted and ignored">
    Graph takes `$select` on mailbox settings, `$filter` on the category list, and
    `$top` and `$filter` on a message's attachments without complaint, and returns
    everything anyway. Those tools do not offer them, because a model handed the
    whole collection reads it as the subset it asked for. The rule list takes
    `$filter`, but most rule properties refuse it with a 400 (`isEnabled`,
    `sequence`); with a handful of rules, list them all.
  </Accordion>

  <Accordion title="A moved message has a new id">
    `messages_move` returns the message in its new folder, under a new id. An id
    saved before the move no longer finds it. `translate_exchange_ids` converts to
    `restImmutableEntryId`, which survives a move.
  </Accordion>

  <Accordion title="$search wants its query in double quotes">
    `search` takes `"pizza"` or `"from:ada subject:invoice"`, quotes included, and
    the call is refused locally without them. It returns at most 1,000 matches,
    most recently sent first.
  </Accordion>

  <Accordion title="Filtering and sorting at once has three rules">
    Graph refuses a `$filter` beside an `$orderby` unless every sorted property is
    filtered on, in the same order, ahead of the others — `InefficientFilter`.
    Newest first with a filter is `orderby="receivedDateTime desc"` and a filter
    that starts `receivedDateTime ge 1900-01-01T00:00:00Z and …`.
  </Accordion>

  <Accordion title="Extended properties live on the item">
    There is no endpoint for one. Write them through `messages_update` or
    `mail_folders_update` (`singleValueExtendedProperties`), and read them with
    `expand="singleValueExtendedProperties($filter=id eq '…')"` on `messages_get`
    or `mail_folders_get`.
  </Accordion>

  <Accordion title="A large attachment is two steps, and the second is yours">
    `attachments_create_upload_session` returns the session's `uploadUrl`. The
    file's bytes go to that URL in `PUT`s of up to 4 MB, which a model has no bytes
    to make; the host does that part.
  </Accordion>
</AccordionGroup>
